# C言語 メモリ配置（メモリレイアウト）

確認環境: macOS 27.0.1（arm64） / Apple clang 21.0.0

## 1. メモリは「ヒープとスタック」だけではない

プログラムのメモリは、大きく次の領域に分かれる。

```
アドレス大
┌──────────────────────┐
│ スタック               │ ローカル変数・引数（アドレスの小さい方へ伸びる）
│          ↓            │
│                      │
│          ↑            │
│ ヒープ                │ malloc で確保した領域
├──────────────────────┤
│ データ領域             │ グローバル変数・static 変数
├──────────────────────┤
│ 読み取り専用データ領域   │ 文字列リテラル・const なグローバル定数
├──────────────────────┤
│ テキスト（コード）領域   │ 機械語になった関数（main など）
├──────────────────────┤
│ __PAGEZERO（4GB）     │ アクセス不可（NULL 参照を検出するため）
└──────────────────────┘
アドレス小
```

| 領域 | 何が置かれるか | いつ確保・解放されるか | 書き換え |
|---|---|---|---|
| テキスト | 関数の機械語 | 起動時に実行ファイルから読み込む | 不可 |
| 読み取り専用データ | 文字列リテラル、`const` なグローバル変数 | 起動時に実行ファイルから読み込む | 不可 |
| データ | グローバル変数、`static` 変数 | 起動時に確保、終了まで存在 | 可 |
| ヒープ | `malloc` で確保したもの | `malloc` で確保、`free` で**自分で**解放 | 可 |
| スタック | ローカル変数、関数の引数 | 関数に入ると確保、関数を抜けると**自動で**解放 | 可 |

- 下の3つ（テキスト・読み取り専用データ・データ）は、ビルド時に中身や大きさが決まり、実行ファイルに書き込まれる。
- ヒープとスタックは、実行中に増えたり減ったりする。

## 2. 実際のアドレスで確かめる

各領域のアドレスを `%p` で表示した結果（並びはアドレス順）。

```c
const int g_const = 10;   // グローバル const
int g_data = 20;          // 初期値ありグローバル
int g_bss;                // 初期値なしグローバル

int main(void) {
    char *ptr = "Hello";
    char arr[] = "Hello";
    const int x = 10;
    static int s = 30;
    void *heap = malloc(16);
    // ... 各アドレスを printf("%p\n", (void *)...) で表示
}
```

| 表示したもの | アドレス | 領域（`nm -m` での表示） |
|---|---|---|
| `main` 関数 | `0x1026d45d0` | テキスト |
| `g_const`（グローバル const） | `0x1026d479c` | 読み取り専用データ（`__TEXT,__const`） |
| `"Hello"`（文字列リテラル） | `0x1026d47bc` | 読み取り専用データ（`__TEXT,__cstring`） |
| `g_data`（初期値ありグローバル） | `0x1026dc000` | データ（`__DATA,__data`） |
| `s`（static ローカル） | `0x1026dc004` | データ（`__DATA,__data`） |
| `g_bss`（初期値なしグローバル） | `0x1026dc008` | データ（`__DATA,__common`） |
| `malloc` した領域 | `0x102ea5560` | ヒープ |
| `ptr` 変数自体（`&ptr`） | `0x16d72a230` | スタック |
| `arr` 配列 | `0x16d72a228` | スタック |
| `x`（const ローカル） | `0x16d72a224` | スタック |
| `main` から呼んだ関数のローカル変数 | `0x16d72a1cc` | スタック |

分かること：

- 文字列リテラルは `main` 関数のコードのすぐ近く（`0x1ec` バイト差）にある。ヒープでもスタックでもない。
- `static` ローカル変数は、関数の中で宣言してもスタックではなくデータ領域に置かれる。
- `const` を付けたローカル変数 `x` はスタックにある（→ 4章）。
- 呼び出された関数のローカル変数は、`main` のローカル変数よりアドレスが小さい。スタックはアドレスの小さい方へ伸びる。

## 3. 文字列の書き方と置き場所

```c
char *ptr = "Hello";   // ポインタ
char arr[] = "Hello";  // 配列
```

| 書き方 | 文字列の置き場所 | 書き換え（`[0] = 'h'`） | 別の文字列を代入 | `sizeof` |
|---|---|---|---|---|
| `char *ptr = "Hello";` | 読み取り専用データ（`ptr` 自体はスタック） | **不可**（未定義動作） | 可（指す先が変わる） | 8（ポインタのサイズ） |
| `const char *ptr = "Hello";` | 同上 | コンパイルエラー | 可 | 8 |
| `char arr[] = "Hello";` | スタック（リテラルからコピーされる） | 可 | 不可（コンパイルエラー） | 6（5文字 + `\0`） |
| `malloc` + `strcpy` | ヒープ | 可 | ― | ― |
| `static char s[] = "Hello";` | データ領域 | 可 | 不可 | 6 |

- ポインタ版で `ptr[0] = 'h';` とすると、読み取り専用領域への書き込みになり `Bus error` で落ちる（終了コード 138 = 128 + SIGBUS(10)）。
- C では文字列リテラルの型は `char[N]`（`const` なし）。歴史的な事情による。そのため `char *ptr = "Hello";` はエラーにならないが、書き換えは禁止されている。誤って書き換えないよう `const char *` と書くのが一般的（C++ ではリテラルは `const char[N]`）。
- 配列は関数に渡すと先頭要素へのポインタに変換される（配列の減衰）。そのため `printf("%s", arr)` も `printf("%s", ptr)` も、`printf` には `char *` が渡る。

## 4. 「定数だから読み取り専用領域」ではない

置き場所は、主に**寿命（いつまで存在するか）**で決まる。`const` は置き場所を決めるものではない。

| 寿命 | 書き換え不可 | 書き換え可 |
|---|---|---|
| プログラム全体（リテラル、グローバル、`static`） | 読み取り専用データ | データ |
| 関数の中だけ（ローカル変数） | スタック（`const` はチェックのみ） | スタック |
| `free` するまで | ― | ヒープ |

- ローカル変数に付けた `const` は、書き換えるコードをコンパイルエラーにするためのもの。置き場所は普通のローカル変数と同じスタック。
- 文字列リテラルが読み取り専用データに置かれるのは、「プログラム全体で存在する必要がある」かつ「書き換えてはいけない」から。
- `int n = 5;` の `5` のような小さな数値リテラルは、メモリに置かれず機械語の命令に直接埋め込まれることが多い。

## 5. スタックの特徴

関数を呼ぶたびに、その関数用の領域（スタックフレーム）が積まれ、関数から戻ると取り除かれる。

```
sub() 実行中             sub() から戻った後
┌──────────┐
│ sub: b   │ ← 積まれる    （取り除かれる）
├──────────┤            ┌──────────┐
│ main: a  │            │ main: a  │
└──────────┘            └──────────┘
```

- 速い（積む・取り除くだけ）。
- 自動で解放されるので `free` は不要。メモリリークにならない。
- サイズが小さい（`ulimit -s` で 8176KB ≒ 8MB）。巨大な配列をローカル変数にすると溢れてクラッシュする（スタックオーバーフロー）。
- 関数を抜けると無効になるので、ローカル変数のアドレスを関数の外へ返してはいけない。

```c
char *bad(void) {
    char s[] = "Hello";
    return s;   // NG: 関数を抜けると s の領域は無効になる
}
```

## 6. アドレスが実行ごとに変わる理由（ASLR）

同じ実行ファイルを2回実行した結果。

```
1回目: main = 0x1026d45d0  文字列リテラル = 0x1026d47bc
2回目: main = 0x10456c5d0  文字列リテラル = 0x10456c7bc
```

```
0x1 026d4 7bc
0x1 0456c 7bc
 ↑   ↑     ↑
 │   │     └ 末尾: プログラム内での位置（オフセット）。ビルド時に決まるので固定
 │   └ 真ん中: 起動ごとに ASLR でランダムにずらされる
 └ 先頭: __PAGEZERO（0x0〜0x100000000）の直後に読み込まれるので固定
```

- **ASLR**（Address Space Layout Randomization）は、起動ごとにメモリの配置をランダムにずらす仕組み。アドレスを予測しにくくして、バッファオーバーランなどの脆弱性を悪用されにくくする。
- ずらすのはページ単位なので、プログラム内での相対位置（下の桁）は変わらない。
- `lldb` などのデバッガ上で実行すると、デフォルトで ASLR が無効になり、毎回同じアドレスになる。
- **`__PAGEZERO`**: 64bit の macOS では `0x0`〜`0x100000000`（4GB）がアクセス不可の領域になっている（`otool -l` で `vmsize 0x0000000100000000`、`maxprot 0x00000000`）。`NULL` やそれに近いアドレスにアクセスすると必ずクラッシュするので、ヌルポインタの誤用にすぐ気づける。

## 7. ビルドすると生成される `.dSYM` とは

`common.mk` の `CFLAGS` に `-g` を付けているため、`make` すると `hello` と一緒に `hello.dSYM` ができる。これは**デバッグ情報の入れ物**で、ファイルではなくフォルダ（macOS のバンドル）。

```
hello.dSYM/
└── Contents/
    ├── Info.plist
    └── Resources/
        ├── DWARF/
        │   └── hello     ← デバッグ情報の本体（DWARF 形式）
        └── Relocations/
```

### 何が入っているか

ソースコードと機械語を結びつける情報。`dwarfdump hello.dSYM` で中身を見られる。

```
DW_AT_name      ("str")
DW_AT_decl_line (2)
DW_AT_type      ("char *")
```

- 変数名・型・宣言した行（上の例は「`str` は2行目で宣言された `char *`」）
- 機械語の各命令がソースの何行目にあたるか
- 関数名とその開始位置

### 何に使うか

- `lldb` でのデバッグ（行番号でブレークポイントを置く、変数名で値を表示する）
- クラッシュ時に「どの関数の何行目で落ちたか」を表示する

実行するだけなら不要。消しても `hello` は普通に動く。

### なぜ別のフォルダになるのか

Linux ではデバッグ情報は実行ファイルの中に入るのが普通だが、macOS では実行ファイルの外に置く。

```
gcc -g hello.c -o hello
  ① コンパイル → 一時的な hello.o（デバッグ情報はここに入る）
  ② リンク    → hello（デバッグ情報はコピーされない）
  ③ dsymutil  → hello.o からデバッグ情報を集めて hello.dSYM を作る
  ④ 一時ファイルの hello.o を削除
```

`gcc -### -g hello.c -o hello` で実際の処理を表示すると、最後に `dsymutil` が呼ばれていることが分かる。一時ファイルの `hello.o` は消えてしまうので、デバッグ情報を `.dSYM` に集めて残している。

| ビルド方法 | `.dSYM` |
|---|---|
| `gcc -g hello.c -o hello` | 作られる |
| `gcc hello.c -o hello`（`-g` なし） | 作られない |
| `gcc -g -c hello.c` → `gcc hello.o -o hello`（2段階） | 作られない（デバッグ情報は `hello.o` に残り、`lldb` はそれを読みにいく） |

- `make clean` で `.dSYM` も削除している（`common.mk`）。
- ビルドのたびに作り直せるので、`.gitignore` で Git の管理対象から外している。

## 8. 確認に使ったコマンド

| コマンド | 分かること |
|---|---|
| `printf("%p\n", (void *)&変数)` | 変数のアドレス（`%p` には `void *` にキャストして渡す） |
| `nm -m 実行ファイル` | グローバル変数・static 変数がどのセクションにあるか |
| `otool -s __TEXT __cstring -v 実行ファイル` | 実行ファイルに埋め込まれた文字列リテラル |
| `strings 実行ファイル` | 実行ファイル内の文字列を一覧表示 |
| `otool -l 実行ファイル` | セグメントの配置（`__PAGEZERO` の大きさなど） |
| `ulimit -s` | スタックの最大サイズ（KB） |
| `dwarfdump 実行ファイル.dSYM` | デバッグ情報の中身（変数名・型・行番号） |
| `gcc -### ...` | `gcc` が内部で実行するコマンド（`dsymutil` の呼び出しなど） |
